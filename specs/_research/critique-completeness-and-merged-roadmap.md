## A. WHAT IS MISSING ACROSS ALL THREE PLANS

### A1. Programs / modalities not actually ported

1. **PatternRepack is demoted to documentation in all three plans.** The user asked for it as "pure code-driven functionality usable from notebooks". A: a private `_sht/_emsphinx_io.py` helper for the regression harness only. B: a notebook sentence ("≡ `kp.load` + `downsample` + `save`"). C: a doc mapping. None reproduces its actual semantics — hard-coded vertical flip, `binAvg` (in-dtype average) vs `binFloat` (sum→float32), dataset name `/patterns`, and **contiguous + `H5D_ALLOC_TIME_EARLY`** so `PatternFile::Read` can take the memory-map fast path (`pattern.hpp:494-507`). Recommendation: one public `kikuchipy.io.write_patterns_for_emsphinx(signal, path, vendor="Bruker", binning=1)` — it is ~40 lines, it is what makes the whole EMSphInx interop story real, and it is the *only* way to feed a kikuchipy h5ebsd file to `IndexEBSD.exe` (whose reader rejects the lowercase `manufacturer = "kikuchipy"` dataset).
2. **EBSPDims is claimed to need no new code (B: "verified"), but the claim is only half true.** kikuchipy's oxford_binary plugin derives the navigation *shape*; `EBSPDims` additionally prints the sorted sets of per-pattern stage x/y and diagnoses the `len(sx)*len(sy) != numPat` (irregular-grid) case. A is the only plan that proposes exposing the coordinates (`get_scan_positions()`), and it does so as a maybe. Either verify that `original_metadata` already carries `beam_x`/`beam_y` per pattern or schedule the 15-line helper.
3. **Non-EBSD `.sht` modalities are invisible in all three plans.** The format carries `modality ∈ {Unknown, EBSD, ECP, TKD, PED, Laue}` and a variable `simMetaSize` (88 for `EMsoftED`, **32 for `EMsoftXD`/Laue**). Every plan's reader hard-codes the 88-byte `EMsoftED` block, so an ECP/TKD/Laue `.sht` (or any future SHTdatabase entry) will mis-parse rather than raise. kikuchipy already ships `ECPMasterPattern` and an `emsoft_ecp_master_pattern` reader, and `MasterPattern::read` (`idx/master.hpp:282-316`) explicitly handles `EMData/ECPmaster`. Minimum: parse `modality`/`simMetaSize` generically, raise `NotImplementedError` for non-EBSD, don't hard-couple `SphericalMasterPattern` to `EBSDMasterPattern`, and state the EBSD-only scope in `specs/mission.md`. Also unhandled everywhere: `numXtal > 1`, big-endian `*SHT`, and `fileVersion != (1,1)` (EMSphInx 0.1 files).
4. **EMSphInx namelist I/O is in one plan only (A/P7).** B never mentions it; C hand-writes `.nml` text in a generation script. Since `IndexEBSD -t` is part of the CLI surface and the namelist is the migration Rosetta stone, a `read_namelist`/`write_namelist` + `SphericalIndexingParameters ↔ (EBSD kwargs, EBSDDetector)` round trip belongs in the visualisation/interop feature — and it is also the cheapest way to prove the four vendor PC conversions.
5. **`psymfile` I/O is missing from all three.** All three *produce* pseudo-symmetry operators; none reads/writes the EMsoft quaternion angle file that `MasterData::addPseudoSym` consumes, so the loop back to `IndexEBSD` is open.
6. **sht2png is only half-ported in B.** B has `to_master_pattern` but no `describe()`/header dump and no stereographic render; the `sht2png` printout is the single best executable specification for a `.sht` parser (and A/C both correctly plan a golden-text test against it).
7. **ROI grammar / `Geometry::ecp()` / IPF+XC PNG writers** are silently dropped by all three. That is defensible, but it should be an explicit scoping line in `specs/mission.md`, not an omission.

### A2. Conventions not honoured

8. **Placement.** A puts the core in a new top-level `src/kikuchipy/_sht/`. kikuchipy has no precedent for a top-level private package; the precedent is `indexing/_refinement/`, `signals/util/`, `similarity_metrics/`. B and C's `src/kikuchipy/indexing/_spherical/` is correct — adopt it.
9. **Local toolchain.** The repo venv is uv-managed with **no pip** (env survey). A and B write `pip install --editable ".[dev]"` and bare `pytest`; only C uses `uv run`. Every command in `specs/tech-stack.md` must be executable as written.
10. **sympy is used as the Wigner oracle (A, C) but is not a declared kikuchipy test dependency.** It is only present transitively. Either add it to `[project.optional-dependencies].tests` (a real change to `pyproject.toml` that needs its own justification) or use B's approach (hard-code the Mathematica tables from `test/sht/wigner.cpp`). B's is better: no dependency, and it is the *same* oracle EMSphInx validates against.
11. **`scipy.special.sph_harm_y` (used as the SHT oracle by all three) requires scipy ≥ 1.15, and `sph_harm` was removed in 1.17.** kikuchipy's CI has an ubuntu/py3.10 "oldest" job (numba 0.57, numpy 1.23, orix 0.12.1, …). No plan version-gates the oracle, so the oldest job will fail on import. Same class of problem: `Orientation.reduce()` (all three) vs the deprecated `map_into_symmetry_reduced_zone` on orix 0.12.1.
12. **`kp.load("*.sht")` works in A and C but not in B** (B exposes only `MasterPatternHarmonics.from_file`). Given kikuchipy's "everything goes through `kp.load`" convention and `doc/tutorials/load_save_data.ipynb`, the io plugin should be in scope.
13. **Ordering nits with real consequences.** B adds `doc/user/bibliography.bib` entries only at F5, so F1–F4 docstrings cannot `:cite:` anything; the PR template's reviewer checklist wants `credits` + `.zenodo.json` in the PR (A defers to P9, B never schedules it). B also does not guard against sweeping the two locally-modified notebooks (`hybrid_indexing.ipynb`, `load_save_data.ipynb`) into a feature commit — A and C both do.
14. **A's `emsphinx_compatible` as a module-level constant** is global mutable state; kikuchipy style is a per-call/per-object keyword. Make it a constructor/keyword argument so parallel tests can exercise both branches.
15. **BSD-3 opt-out.** `doc/dev/licensing_considerations.rst` instructs reviewers to check "whether contributors are aware they can opt for BSD licensing instead of GPL". Every PR here must state up-front that BSD is *impossible* for this code. All three mention the GPL lineage; none pre-empts that specific reviewer prompt.

### A3. Tests without real data / untested branches

16. **Only cubic symmetry is ever exercised on real data.** Ni gives `zRot=4, mirror=True, cmpFlg=0x7`. The `.sht` packer branches on `mirY (0x04)` → strictly-real rows and `mirX (0x08)` → alternating real/imaginary rows, and on `zRot ∈ {1,2,3,6}`. Every kikuchipy public master pattern is cubic (or tetragonal 4/mmm for `steel_sigma`), so **`zRot ∈ {3,6}`, `mirror=False`, and both mirX/mirY packing branches ship untested.** Cheap fix: generate one tiny synthetic `.sht` per distinct `(zRot, cmpFlg)` produced by the `SpaceGroupRot/Cmp` LUTs with our own writer, and byte-verify each with `sht2png.exe`. The local hcp masters (`openECCI_RKD/data/Mg-master-17kV.h5`, `Ti-alpha-master-20kV.h5`) can back a skip-if-absent local test but cannot be the CI safety net.
17. **Nobody runs the EMSphInx binaries on *our* output.** All three validate EMSphInx → kikuchipy only. Feeding a kikuchipy-written `.sht` to `sht2png.exe` and to `IndexEBSD.exe` is the strongest, cheapest possible validation of the writer, packer and CRC — and it is the only test that proves the deliverable is genuinely interoperable. Add it to the regression feature (as a locally-gated test).
18. **The ported preprocessing is never validated against EMSphInx.** `nregions=10` is the `IndexEBSD` **default**. A and C port mosaic AHE + Gaussian background but validate them only against synthetic inputs / a loose skimage comparison; B does not port them at all and therefore cannot reproduce any default-settings EMSphInx run. Generate references at `nregions ∈ {0, 4, 10}` and require the ported-AHE path to match the `nregions=10` reference end-to-end — that is the only oracle available.
19. **No test covers the `navigation_mask`/ROI path against an EMSphInx run with `roimask` set**, and no test covers per-pattern failure handling (EMSphInx catches per-pattern exceptions and writes `phase = -1`, identity, metric 0). None of the three defines what `spherical_indexing` does on a failed/zero-variance pattern or how that maps to `CrystalMap.is_indexed`.
20. **Feature-1 real-data tests are weak in A and B.** A's is a bw=200 Lambert RMS check that it admits should move to P2; B's F1 real-data test is a ≥0.99 correlation after regridding. C's "m-3m systematic zeros in the Ni power spectrum (`m % 4 != 0` and odd `l+m` below 1e-6)" is the best of the three — it is real data, it is cheap, and it fails loudly on a Condon–Shortley or ring-ordering error. Adopt C's.

### A4. Unanswered technical questions / unverified claims

21. **`slP = fastSize(2·bw−1)` — three different definitions, one of them likely wrong.** A and C implement EMSphInx's own {2,3,5,7,11,13}-smooth search; B uses `scipy.fft.next_fast_len(2*bw-1, real=True)`, which restricts to a smaller radix set and will return a **larger** `slP` for several recommended bandwidths. `slP` sets the entire Euler grid (`α = 2πm/slP − π/2`, …), so a mismatch silently changes results and destroys reference parity. Resolve in feature 1 with a five-line sweep of `fastSize` (`util/fft.hpp:438-491`) vs scipy over bw ∈ [16, 512].
22. **Legendre ring quadrature weights: the plans directly contradict each other.** C states flatly that `computeWeightsSkip`'s Sneeuw solve must be ported "because the hemisphere rule with the equator node included is not the plain Gauss–Legendre rule". B drops `computeWeightsSkip` entirely for "`leggauss` weights, pole 0, equator halved" with a one-off cross-check. This is a load-bearing numerical assumption for every downstream tolerance and must be settled **before** any SHT code is written, not validated afterwards.
23. **Back-projection LUT direction is a correctness issue, not a style one.** EMSphInx *gathers*: it iterates the `dim²` Legendre sphere normals and asks `interpolatePixel` whether each lands on the (√2-oversampled) detector (`detector.hpp:502-569`). A gets this right explicitly. C's `_build_backprojection_lut(directions, …)` plus its test `test_lut_directions_match_detector` (LUT directions ≡ `_get_direction_cosines_from_detector` to 1e-12) implies a **scatter** from detector pixels into sphere bins, which leaves unfilled sphere pixels wherever the sphere is finer than the resampled detector. B is internally inconsistent — its back-projection design says "build the LUT from `detector.sample_to_detector` + gnomonic bounds" (gather, correct) while its reuse list and tests lean on `_get_direction_cosines_from_detector` (scatter). Pin this in the spec: gather, with `_get_direction_cosines_from_detector` used only as an independent cross-check at pixel centres.
24. **Per-point projection centre.** `nickel_ebsd_small` and `nickel_ebsd_large` both carry per-point PC arrays, and the bundled reference `xmap` was produced with them. All three plans index with `pc_average` and then assert misorientation tolerances against that reference **without ever measuring the mean-PC error floor**. Either measure it first (trivially: re-run kikuchipy's own refinement with mean PC and record the spread) or support varying PC by grouping patterns per unique PC and rebuilding the LUT — otherwise every tolerance in §D of every plan is a guess.
25. **"`Manufacturer='Bruker'` ⇒ `flp=false` ⇒ consistent with kikuchipy row order and Bruker PC"** is asserted by all three and verified by none. It is the single most likely source of a mirror/180° error, and it silently poisons every reference file. All three do have a forward-projection convention test — schedule it *before* generating any reference, and add an asymmetric-pattern check.
26. **"`delta` is geometry-neutral for fractional PC"** (A uses 100, C uses 500, B uses 480). Verify by generating one reference at two `delta` values and diffing.
27. **B's claim that spherical back-projection supports `azimuthal`/`twist`** (a superset of EMSphInx, which throws on `dOmg/sOmg != 0`) is attractive but untested and, by construction, unverifiable against any EMSphInx reference. Ship it as an explicitly unvalidated extension or raise for now.
28. **The CMU provisional patent status was never checked by anyone.** The licensing survey flags it as the top risk and notes no granted patent was found; a provisional lapses at 12 months unless converted. Checking Google Patents/USPTO Patent Center (inventors Lenthe/Singh/De Graef, assignee CMU) is a 10-minute task that belongs in the constitution phase, before the pyxem issue is opened.
29. **A `.sht`-derived `EBSDMasterPattern` has no energy axis and a Legendre-origin grid**; all three assert `.plot()` (and A implies `get_patterns()`) will work. Unverified.
30. **`scores` semantics.** EMSphInx's metric is not divided by the pattern norm (`Indexer::sum2` is dead), so it is *not* a [0,1] NCC and is only comparable within a fixed geometry. Only A pins a range. This must be in the `CrystalMap` prop docstring, and note that `orientation_similarity_map` cannot be used (no `simulation_indices`).
31. **B's full-cube `irfftn` doubles peak memory at high bandwidth and discards the `dx=flmFold` optimisation** (4× fewer 2-D transforms for m-3m), which it defers as "measure first". Combined, that puts B's own ≥10 pat/s/thread target at risk; it needs a hard gate, not a footnote.
32. **Minor but real:** `circmask=0` in EMSphInx applies the circle to the *DCT-rescaled* geometry, whereas a kikuchipy `signal_mask` is applied at native resolution — the covered solid angle differs slightly; and `signal_mask` polarity (True = ignore) is stated only by B.

## C. CLARIFYING QUESTIONS FOR THE USER (6)

**Q1 — Fidelity axis.** Should the port reproduce EMSphInx's result-affecting quirks (the 2× master mean over `totW`, quartered corner weights, the `interpPeak` `x[2]` bounds bug, the Gaussian-fit off-by-one, the metric not normalised by the pattern norm) *and* port its preprocessing (mosaic AHE, 2-D Gaussian background, DCT image quality), or fix/replace them with kikuchipy equivalents?
*Recommended default:* port everything faithfully behind a per-call `emsphinx_compatible=True` keyword (not a module global), so the regression can be tight and `nregions=10` — EMSphInx's own default — is reproducible; document each quirk and recommend kikuchipy's `remove_*_background`/`adaptive_histogram_equalization`/`get_image_quality` as the idiomatic path in the tutorial.

**Q2 — Projection centre.** Support per-point PC in back-projection from v1 (group patterns by unique PC, rebuild the LUT per group), or require a single mean PC and raise otherwise?
*Recommended default:* v1 = single PC with a `ValueError` that names `detector.pc_average`; but **first** measure the mean-PC error floor on `nickel_ebsd_small`/`nickel_ebsd_large` and set every misorientation tolerance from that measurement rather than from a guess. Varying PC lands as a follow-up feature.

**Q3 — Deliverable target and legal gate.** Fork-only research code, or an upstream PR series to `pyxem/kikuchipy`? And do we block public code on the CMU provisional-patent check?
*Recommended default:* develop on the fork with PRs into the fork's `develop`; at feature 0, run the Google Patents/USPTO check, open a `pyxem/kikuchipy` issue referencing EMSphInx issue #7 (hakonanes, 2020, still unanswered), and email `pyxem.team@gmail.com` about the GPL-2.0-or-later → GPL-3.0-or-later relicensing *and* the patent statement; commit `specs/` on the fork only and strip it from any upstream PR.

**Q4 — Public API surface and names.**
*Recommended default:* `EBSDMasterPattern.get_spherical_harmonics(...) -> kikuchipy.indexing.SphericalMasterPattern`; `EBSDDetector.get_spherical_indexer(...) -> kikuchipy.indexing.SphericalIndexer` (mirroring `get_indexer`); `EBSD.spherical_indexing(indexer, navigation_mask=None, n_best=1, ...)` and `EBSD.refine_orientation_spherical(xmap, indexer, ...)`; `kikuchipy.indexing.find_pseudo_symmetry_operators(...)`; plus a `.sht` io plugin so `kp.load("x.sht")` returns an `EBSDMasterPattern`. Keep the SHT/Wigner/correlator/back-projector **private** under `src/kikuchipy/indexing/_spherical/` (matching the `_refinement/` precedent — not a new top-level `_sht/`).

**Q5 — Reference-data hosting and redistribution.** In-package, `pyxem/kikuchipy-data`, or fork-local behind an env var? And may `EMSphInx/data/Ni {20kV 75.7deg}.sht` be redistributed inside kikuchipy as a parse fixture?
*Recommended default:* ship a freshly generated `ni_20kv_bw384.sht` (~75 kB), the synthetic per-`(zRot, cmpFlg)` `.sht` fixtures, and the `.npz` indexing references (~100 kB total) in-package under `src/kikuchipy/data/emsphinx/` with md5s in `_registry.py` and no URLs; keep the EMSphInx-shipped `.sht`, the MasterXcorr volume and the hcp masters local behind `EMSPHINX_ROOT`/`KP_LOCAL_DATA` with `pytest.skip`; move to `kikuchipy-data` only if maintainers ask.

**Q6 — Performance floor and CI compatibility.** What is the v1 throughput target, and must the Python-3.10 "oldest" CI job (numba 0.57, numpy 1.23, orix 0.12.1, old scipy) stay green?
*Recommended default:* gate feature 6 at **≥10 patterns/s/thread at bw=68** (≈1 min for `nickel_ebsd_large` on 8 threads) with the benchmark as the gate, and keep the oldest job green by version-gating the `scipy.special.sph_harm_y` and `Orientation.reduce()` test oracles (`pytest.importorskip` / `Version` checks) rather than dropping them; defer any float32 fast path and the `dx=flmFold` FFT-plane skipping to a measured follow-up.
