ADVERSARIAL REVIEW — "faithful-port" plan for EMSphInx spherical indexing into kikuchipy

Verification was done against `c:/Users/westraadt.1/Repos/kikuchipy` @ 49b1c11c and `c:/Users/westraadt.1/Repos/EMSphInx` @ 60f3517. Claims I could confirm are noted as such; everything below that is marked BLOCKER/MAJOR was checked in the source, not inferred from the reports.

BLOCKERS
====================================================================

B1. The ZYZ -> orix Euler mapping in section C is WRONG, and it is labelled "verified".
Plan text: "Equivalent, verified formula: `Rotation = ~Rotation.from_euler([alpha-pi/2, beta, gamma+pi/2])`", and `_euler.py: zyz_to_bunge(zyz) -> (alpha-pi/2, beta, gamma+pi/2)`.
Evidence: `c:/Users/westraadt.1/Repos/EMSphInx/include/xtal/rotations.hpp:973-989` (`zyz2qu`) uses sigma=(g+a)/2, delta=(g-a)/2, `qu = [c*cos(sigma), -s*sin(delta), -s*cos(delta), -c*sin(sigma)]`; `rotations.hpp:409-429` (`eu2qu`, Bunge) uses sigma=(eu0+eu2)/2, delta=(eu0-eu2)/2, `qu = [c*cos(sigma), -s*cos(delta), -s*sin(delta), -c*sin(sigma)]`; `rotations.hpp:1025-1032` (`zyz2eu`) gives eu = (a-pi/2, b, g+pi/2).
Numeric check with (a,b,g) = (0.3, 0.7, 1.1): `zyz2qu` -> [0.71844, -0.13353, -0.31583, -0.60516]; `eu2qu(zyz2eu(...))` -> [0.71844, +0.13353, +0.31583, -0.60516]. The x and y components are sign-flipped, i.e. the two differ by a 180 deg conjugation about z — a genuinely different orientation once the sample frame is fixed. Substituting eu = (a+pi/2, b, g-pi/2) reproduces `zyz2qu` exactly.
So EMSphInx's own `zyz2eu` is inconsistent with its `zyz2qu` (the `//@note` at rotations.hpp:971 asserting equivalence is wrong), and `Indexer::indexImage` (`include/idx/indexer.hpp:264`) uses `zyz2qu`, not the Bunge path. Porting `zyz_to_bunge` faithfully and then using it for the orix boundary yields orientations rotated 180 deg about sample-Z relative to `IndexEBSD.exe`. IPF-Z maps would look identical; IPF-X/Y would be systematically wrong. The plan's P3 tests (`zyz_to_bunge`/`bunge_to_zyz` round trip, `rotate_harmonics` round trip) cannot catch this because both are self-consistent.
Fix: make `zyz_to_quaternion` (port of `zyz2qu`) the single source of truth for the orix boundary; state the Bunge equivalent as `(alpha+pi/2, beta, gamma-pi/2)`; add an explicit P3 test asserting `zyz_to_quaternion(zyz) == Rotation.from_euler(zyz_to_bunge_for_orix(zyz)).data` for a random batch, and keep the faithful `zyz2eu` only for `extractBunge`/plot cubes with a comment documenting the upstream inconsistency. Remove the word "verified" from any claim not backed by an executed check.

B2. The PC "fact verified during planning" is wrong by a factor of `binning`, and contradicts the plan's own P4 spec.
Plan preamble: "`EBSDDetector._pc_bruker2emsoft(version=4)` gives exactly EMSphInx's `cX=(x*-0.5)w, cY=(0.5-y*)h, sDst=z*·h·pX`".
Evidence: `c:/Users/westraadt.1/Repos/kikuchipy/src/kikuchipy/detectors/_ebsd_detector.py:2326-2333` returns `x = (0.5-pcx)*ncols*binning` (negated for version<5, so version 4 gives `(pcx-0.5)*ncols*binning`), `y = (0.5-pcy)*nrows*binning`, `z = pcz*nrows*binning*px_size`. kikuchipy's emsoft xpc/ypc are in UNBINNED pixels; EMSphInx's cX/cY are in BINNED pixels (`Geometry::bin` at `include/modality/ebsd/detector.hpp:304-326` divides cX,cY by n while multiplying pX by n). For `nickel_ebsd_small` (binning=8) cX/cY would be 8x too large — the pattern centre would land far off the detector. Only `sDst` matches (pX cancels).
Note the plan's own P4 text writes the correct binned form (`cX=(pcx-0.5)*ncols`, `sDst=pcz*nrows*px_size_binned`). Fix: delete the `_pc_bruker2emsoft` claim from the constitution facts, derive the geometry from `pc`/`shape`/`px_size_binned` directly as in P4, and add a P4 unit test pinning the binned/unbinned distinction (`binning != 1` case) — otherwise this passes on synthetic 1x binning detectors and fails only on real data.

B3. The `.sht` format code is BSD-3-Clause (SHTfile), not GPL (EMSphInx) — the licensing plan misattributes it, and the proposed placement creates a policy conflict.
Evidence: `c:/Users/westraadt.1/Repos/EMSphInx/build/_deps/shtfile-src/LICENSE` is a 3-clause BSD notice, "Copyright (c) 2019, De Graef Group, Carnegie Mellon University / Author William C. Lenthe". Everything the plan lifts for P2's I/O — the byte layout, the CRC-32C LUT (`sht_file.in.hpp:947-1005`), `PackHarm`/`UnpackHarm` (`:1706-1831`), and the 230-entry `SpaceGroupRot`/`SpaceGroupCmp` LUTs (`:1838-1869`) — comes from that BSD repo, fetched by `CMakeLists.txt:151-162`, not from GPL EMSphInx.
Consequences the plan misses: (a) the required notice is the BSD copyright + disclaimer, not "GPL-2.0-or-later, relicensed"; (b) `src/kikuchipy/io/plugins/emsphinx_sht/` is misnamed (the format is EMsoft/SHTdatabase `.sht`, produced by SHTfile) — call it `emsoft_sht` or `sht`; (c) the plan's `file_writer` computes harmonics, which drags GPL `_sht` into what could otherwise be a permissive plugin — decide deliberately and record it, since kikuchipy's `doc/dev/licensing_considerations.rst` (on upstream develop; confirmed ABSENT from the local `doc/dev/`, so the local clone cannot have been checked) forbids BSD components importing GPL code.
Also: the plan cites line numbers into `build/_deps/shtfile-src/`, an ephemeral CMake fetch dir that will not exist on a clean clone. Pin the upstream repo URL + commit SHA in `specs/`.
Fix, and a precedent the plan should reuse rather than invent: `c:/Users/westraadt.1/Repos/kikuchipy/src/kikuchipy/signals/util/_master_pattern.py:19-56` already carries the kikuchipy GPL header followed by a delimited third-party BSD block plus an explicit "the following functionality in this file is derived and adapted from EMsoft" list. Copy that exact pattern (GPL header + delimited CMU notice + enumerated derived functions) for both the GPL EMSphInx-derived files and the BSD SHTfile-derived files. It also demonstrates the `licenseheaders` hook coexists with a trailing third-party block.

B4. Per-point projection centres are unhandled and unspecified.
`EBSD.spherical_indexing(..., detector: EBSDDetector, ...)` builds one `SphericalBackProjector` and, for `normalize=True`, one `mlm`/`rDen` per phase. Both are functions of the PC and the signal mask. But `kp.data.nickel_ebsd_small()` and `nickel_ebsd_large()` both ship nav-shaped `detector.pc` ((3,3,3) and (55,75,3)), and kikuchipy's refinement API supports varying PC. The plan silently uses `pc_average` in its own tests without stating the API contract.
Fix: specify the behaviour explicitly in P5's requirements — either raise a `ValueError` naming the given `pc.shape` and telling the user to pass `detector.pc_average` (cheapest, matches EMSphInx's one-PC-per-scan model), or support grouping by unique PC with one LUT/rDen per group and document the cost. Add a test for whichever you choose. Right now this will silently index with a wrong geometry or crash deep in the LUT builder.

M1. `pre-commit run --all-files` (mandated in tech-stack "Commands" and in the per-feature workflow) will run the `licenseheaders` hook over the entire repo.
Evidence: `.pre-commit-config.yaml:34-38` installs `licenseheaders -t .license.tmpl -cy -n kikuchipy -f`; the `skip: [licenseheaders]` at `:45` is under the `ci:` key only — it does not apply to local runs. The repo TODO ("Remove skip once (nearly) all files are formatted") shows the header state is inconsistent, so a repo-wide run produces a large unrelated diff that will contaminate every feature commit.
Fix: mandate `pre-commit run --files $(git diff --name-only --cached)` (or `--from-ref/--to-ref`), and add an explicit "no files outside the feature's file list may appear in the commit" gate to each `validation.md`.

M2. `emsphinx_compatible` as a module-level boolean constant is broken under numba and off-convention.
The plan puts each faithful-quirk switch "behind an `emsphinx_compatible: bool = True` module constant/flag ... in `_sht/__init__.py`", while also requiring `@njit(cache=True)` kernels. Numba freezes module globals at compile time; flipping the flag at runtime has no effect on already-compiled (or cached) kernels, and a `cache=True` function whose behaviour depends on a global is a correctness trap across sessions. It is also contrary to kikuchipy style (explicit keyword arguments with documented defaults, e.g. `operation=`, `normalize=`).
Fix: pass the flag as an explicit kernel argument or select between two compiled kernels; expose it as a keyword on the public functions (`weighted_normalize(..., emsoft_mean_bug=True)`, `interpolate_peak(..., faithful_bounds_check=True)`), and enumerate every quirk with its default in one docs table.

M3. Performance targets and the notebook runtime budget are optimistic and are load-bearing for the deliverable.
EMSphInx's own cost model (`include/idx/indexer.hpp:189-205`, `k = 1e-8`, complexity `bw^3 ln(bw^3)`) predicts ~25 pat/s/thread at bw=68 for tuned C++ with FFTW and cache-blocked kernels; the measured CPU benchmark is 655 pat/s on 20 threads at bw=55. The plan targets ">= 15 pat/s/thread" for a numba/scipy port and a notebook that indexes 4125 patterns in "30-60 s with 8 threads" plus a bandwidth sweep, DI/HI comparison, refinement and pseudo-symmetry, all inside "< 5 min on a laptop". Newton refinement is ~50 % of EMSphInx's time and is the hardest part to make fast in numba (per-iteration `dTablePre` is O(bw^3) with scalar recursions). "Near-linear scaling like EMSphInx's ThreadPool" is also asserted, not measured — dask block overhead plus a Python per-pattern loop typically caps this well below linear.
Fix: add a mandatory performance spike at the end of P3 (single-pattern `correlate` timing at bw=53/68/88, measured, recorded in `validation.md`), and make P9's notebook budget conditional on it, with a pre-agreed fallback (bw=53, `s.inav[:40, :30]`, `refine=False` for the sweep cells). State explicitly that the benchmark target is informational, not a gate — the plan says this in one place and contradicts it with the notebook budget in another.

M4. Several "tasks" are unresolved deliberation, not executable specs — this violates the SDD requirement the user asked for.
Examples verbatim from the plan: P5 test 4 "90 deg about [1,0,0] hmm—for cubic that's a symmetry; use a synthetic low-symmetry phase ... — or reuse ... treated as if triclinic"; P5 test 5 "`[smp_ni, smp_ni.rotate(...)]`? — better `[smp_ni, smp_si]`"; P2 test "systematic zeros (`alm[m % 4 != 0] == 0` within 1e-10 after enforcing? — no: verify they are <= 1e-6·max"; P7 "`write_emsphinx_pattern_file(...)` in `kikuchipy_h5ebsd/_api.py`? Better: `_sht/_emsphinx_io.py` ... exposed as `kp.io.plugins.emsphinx_patterns`? Keep private"; P1 "this test moves to P2"; P0 "new `doc/dev/porting_emsphinx.rst`? — no: instead a NOTICE-style paragraph".
Fix: resolve each before writing the corresponding `requirements.md`; a task that still contains a question mark is not approvable. This is exactly what the plan-approve-spec gate exists to catch.

M5. Real-data coverage is thinner than the user's requirement in P1, P3, P6 and P7.
P1's only real-data test is deferred or hand-waved ("this test moves to P2"), and the substitute — SHT of the 401x401 Ni master pattern on the LAMBERT layout at dim=401, bw=200 — is beyond anything EMSphInx itself tests (its `test/sht/square_sht.cpp` caps Lambert at bw=128, i.e. dim=257) and risks tripping the weight-solve precision guard at `include/sht/square_sht.hpp:1058` ("insufficient precision to accurately compute ring wieghts", threshold cbrt(eps)/64), which the report itself calls "the practical bandwidth ceiling for the Lambert grid in double precision". P3 explicitly defers its real-data convention test to P4/P5. P7's real test compares `summary()` against a golden string captured from `sht2png.exe`, a local-only binary.
Fix: for P1 use the Legendre layout at a realistic indexing size (dim=71/91) on the Ni master pattern regridded with a minimal inline `to_legendre` helper, or accept that P1 is a pure-math feature and say so in `requirements.md` rather than inventing a fragile real-data test. For P3, add a cheap real-data test now (analyze the Ni master at bw=68, autocorrelate, assert the identity peak and the 24 cubic operators) instead of deferring.

M6. `flm2`, `mlm` and `rDen` construction is missing from P5's task list, and their PC/mask dependence is not stated.
The normalized correlator needs, per phase, `flm2 = SHT(f^2)` (synthesize -> square -> analyze at the indexing dim) and one `mlm` = SHT of the binary detector footprint, from which `rDen` (a `(bwp, slp, slp)` array, same size as `xc`) is derived (`include/sht/sht_xcorr.hpp:1182-1204`, `include/modality/ebsd/idx.hpp` step 12). `mlm`/`rDen` change whenever the PC, the signal mask or the circular mask changes. P5's file list and `_SphericalIndexingSetup` description do not mention any of this.
Fix: add explicit construction tasks and a test that changing `signal_mask` changes `rDen` (and hence the scores), which also documents why per-point PC is expensive (B4).

M7. Memory table understates per-worker usage by roughly 2x.
The table lists ~37 MB/worker at bw=68 and ~165 MB at bw=113, then admits in a parenthesis that `tmp` is "of the same size as fxc". Including `tmp` (and the `xc*rDen` temporary the plan's `np.argmax(xc*r_den)` allocates), bw=113 is ~250 MB/worker, so 8 threads is ~2 GB plus shared tables, not the stated 1.5 GB. On a 16 GB laptop with a phase list of 2-3 this becomes the binding constraint.
Fix: recompute the table with `tmp` included, do the `xc *= rDen` multiply in place as EMSphInx does (single pass with running argmax), and add a documented memory-estimate helper plus a warning when the estimate exceeds available RAM.

MINOR

m1. The P1 solid-angle test invariant is arithmetically wrong. `ring_solid_angles` returns Nt per-ring values normalised by the average pixel solid angle, so the correct invariant is `sum_y w_y * N_phi(y) ~= (2*dim^2 - 4*(dim-1))/2` (plus the equator band), not `sum(w) == 2*dim^2 - 4*(dim-1)`; likewise `lambert_pixel_solid_angles` (dim*dim, one hemisphere) sums to ~dim^2. As written the test fails on day one.

m2. `fast_size` and scipy radix support. EMSphInx allows 13-smooth sizes (`include/util/fft.hpp:438-491`); scipy/pocketfft has fast radices 2,3,4,5,7,11 and falls back to Bluestein for 13 — a "fast" size by EMSphInx's rule can be slow in scipy. For every recommended bandwidth (53, 63, 68, 74, 88, 95, 113, 123, 158) `2*bw-1` is already 7-smooth so the default path is unaffected; note the caveat and add a check that warns when `slp` has a factor of 13.

m3. The `.sht` "read -> write -> read byte-identical" test is underspecified: `save()` defaults `notes="created with kikuchipy"` and the 8-byte `softwareVersion` field is the writer's git hash, so byte-identity requires a passthrough mode that preserves everything read. Specify a `preserve_header=True` path or weaken the assertion to field-wise equality plus CRC.

m4. Asserting kikuchipy's `summary()` equals `sht2png.exe`'s printout format couples a public repr to a C++ program's formatting for no benefit. Assert the decoded field values instead.

m5. `kp.data.emsphinx_reference_indexing(name)` as a public data loader is the wrong home for test fixtures. Keep the `.npz` references under `tests/` (or `kikuchipy-data`); a public API that exists only to serve a regression test is API surface you must then maintain and deprecate.

m6. `sympy.physics.wigner.wigner_d_small` convention is not pinned. EMSphInx's `d^j_{k,m}` matches Mathematica `WignerD[{j,k,m}, gamma, beta, alpha]`; sympy's small-d differs by transpose/sign for some index orders. A 1e-12 tolerance against an unverified convention will burn a day. Pin the mapping with the hard-coded Mathematica tables already present in `c:/Users/westraadt.1/Repos/EMSphInx/test/sht/wigner.cpp` (which is the authoritative reference and needs no new dependency).

m7. `scores in (0, 1.2]` and `iq in [0,1]` are asserted a priori. The EMSphInx CPU benchmark metric range was 0.32-0.74 while a different build produced 4.4-4.8; and `imageQuality` (`util/image.hpp:489-507`) is `1 - vIq/(...)` with no clamp, so it can go negative. Measure first, then pin.

m8. `EBSDMasterPattern.get_spherical_harmonics(bandwidth=384)` will raise "insufficient grid resolution" (`include/idx/master.hpp:559`) for any master pattern smaller than 387 px. `nickel_ebsd_master_pattern_small` is 401 px so it just passes; anything smaller does not. Either lower the default or make the error message name the given `npx` and the required `dim_lg`.

m9. "PatternRepack ≡ `kp.load` + `EBSD.downsample` + `save`" is not an equivalence. `programs/pattern_repack.cpp` hard-codes a vertical flip, uses in-type average binning (`binAvg`), and creates the dataset with `H5D_ALLOC_TIME_EARLY` contiguous layout so EMSphInx's offset-based streaming path works. Since P8's reference generation depends on this, specify the exact writer rather than asserting equivalence.

m10. `EBSPDims` is largely already covered: `src/kikuchipy/io/plugins/oxford_binary/_api.py:307-311` derives the scan grid from `beam_x`/`beam_y` and `:513-516` exposes them in `original_metadata`. P7 should document the existing capability rather than plan a new helper.

m11. `ShtWisdom` is in the user's request ("wisdom-equivalent if meaningful") but is never explicitly dispositioned anywhere in the plan. Record an explicit "not applicable — scipy/pocketfft needs no planning; the fast-bandwidth table is carried instead" decision in `specs/mission.md` so the coverage claim is auditable.

m12. `.sht` `zRot`/`cmpFlg` come from space-group LUTs (`SpaceGroupRot`/`SpaceGroupCmp`) while the correlator's `fNf`/`fMr` come from the point group (`include/idx/master.hpp:185-189`). P2's `_symmetry.py` merges both into one table without saying so; they can disagree for non-standard settings. Keep them separate and test the disagreement case.

m13. `Manufacturer` string encoding for the P8 repack: EMSphInx reads a variable-length string with a 128-byte fixed fallback (`include/modality/ebsd/pattern.hpp:627-636`). h5py's default `str` is variable-length UTF-8; verify `IndexEBSD.exe` accepts it before generating references (a 5-minute check that saves a confusing failure).

m14. `n_workers` on `EBSD.spherical_indexing` deviates from kikuchipy's convention (DI and refinement rely on the dask config). Drop it or justify it in the spec.

Correctly rejecting `EMSphInx/benchmarks/GPU_test_*` (missing inputs, different branch, incompatible metric scale) and generating a fresh single-threaded CPU reference instead; recording the EMSphInx commit, nml text and log header inside the `.npz`; sizing the shipped artefacts (75 kB `.sht`, ~100 kB `.npz`) to fit kikuchipy's in-package data convention with md5s in `_registry.py`. The `delta=100` ratio-invariance argument for the reference nml is correct (pX cancels in `interpolatePixel`).

The plugin `specification.yaml` claim is correct — every existing plugin has one.
